Four rings around a model

An agent is a model, harnessed, in an environment. This guide walks through each ring using the code and real runs from ~/projects/harness-lab. Then it covers the most interesting question for local models: where a better harness pays off most, and which agents to build next.

    Harness lift shrinks as models improve

    Better instructions doubled the 3B model's score and helped qwen3:14b a little. The two models that already scored 8/8 had nothing left to gain.

    Environment help has to fit the model

    Tests and AGENTS.md took qwen3:14b to 8/8 in every run. The same folder dropped llama3.2:3b to zero: it tried to copy a regex tip from AGENTS.md and broke the quotes, so its file wouldn't even load.

    Newer beats bigger

    qwen3.5:9b scored 8/8 with no help, at about 10 seconds a run. qwen3:14b is half again as big and averaged 5.3 in the same setup.

    This task is now too easy

    Two of four models ace it with a one-line prompt, so it can't show what a harness adds for them. Measuring harness changes on good models needs harder tasks.

    Which local model gains most from a harness?

    The best model for this lab is not the strongest one you can fit. You want a model that can call tools reliably but still makes mistakes a harness can fix. If it never makes those mistakes, the harness has nothing to improve. If it can't call tools at all, no harness helps.

    Recommendation

    Use qwen3.5:9b as your main lab model. It scored 8/8 in every run at about 10 seconds each, so you can repeat experiments many times. Because it already solves slugify alone, you'll need harder tasks to see what harness changes do for it.

    Keep llama3.2:3b as a fast early warning. It reacts to almost every harness or environment change, in both directions, within seconds. Keep gemma4:26b for checking whether a new task can be solved at all.

    macOS keeps part of the 24 GB for itself, so anything above about 16 GB is a squeeze. Those models still run, but with less room for context.

    Harness upgrades

    What helps local models most

    Small models lose the plot faster than frontier models. These are harness-side fixes, ordered roughly by how much they're likely to help. Each one is a small, testable change in src/harness/.

    Loop detection

    Spot the same failing tool call repeating and inject a nudge: "You've tried this 3 times. Re-read the error." Runs in examples 5 and 6 hit the 16-turn limit doing exactly this. not built

    Automatic verification

    After every write_file, the harness runs the tests itself and appends the result. The model no longer has to remember to check. not built

    Fewer, sharper tools

    Each extra tool is another chance to pick wrong. Give each agent the minimum set, with an example in every description. partly: per-agent tool sets

    Edit instead of rewrite

    An edit_file (find and replace) tool. Small models mangle long files when they rewrite them whole. not built

    Validate tool arguments

    Check arguments against the schema before running. Return exactly what's wrong so the next turn can fix it. partly: unknown tools only

    Constrained output

    Ollama's format option forces JSON that matches a schema. Use it for plans and final answers, where small models drift. not built

    Context hygiene

    Summarise old turns instead of dropping them, and shrink big tool outputs first. partly: drop oldest, cut long outputs

    Sub-agents

    A tool that starts a fresh agent with a narrow task and returns only its answer. Keeps each context small and focused. not built

    What to build

    Agents that suit a local model

    Local models do best with a narrow job, a small tool set and an environment that gives clear feedback. These start safe (read-only) and get riskier as they gain the power to change things.

    Repo explorer

    built: explorer

    Reads a codebase and answers questions about it. Example 3 points it at harness-lab itself.

    Tools
    list_dir, read_file, + tree
    Risk
    low, read-only
    Ring to improve
    harness: a tree tool stops it guessing paths

    Test-driven builder

    built: builder

    Writes code, runs it, fixes it. The workhorse, and the best place to measure harness changes.

    Tools
    files, run_shell, + edit_file
    Risk
    medium, shell approval
    Ring to improve
    environment: tests; harness: auto-verify

    Code reviewer

    next

    Reads a git diff and lists likely bugs. Read-only, so it's safe to run on any of your projects.

    Tools
    read_file, git_diff
    Risk
    low, read-only
    Ring to improve
    model: try thinking on vs off

    Notes librarian

    next

    Answers questions over a folder of markdown, such as your yt-knowledge-base or music-kb. Uses nomic-embed-text, already installed, for search.

    Tools
    search_notes, read_note
    Risk
    low, read-only
    Ring to improve
    environment: a search index

    Data analyst

    later

    Given a CSV, writes and runs small Node scripts to answer questions about it, and checks its own numbers.

    Tools
    read_file, run_shell
    Risk
    medium, runs code
    Ring to improve
    harness: constrained final answers

    Orchestrator

    later

    Splits a job and hands pieces to explorer, builder and reviewer as sub-agents. An agent in a harness inside an agent.

    Ring to improve
    agent: clear hand-off rules
    Next steps

    A path through the lab

    In order, because each step gives you something to measure the next one with.

    1. Get the lab model

      qwen3.5:9b is installed. Use it anywhere with an environment variable.

      HARNESS_MODEL=qwen3.5:9b npm run chat
    2. Measure harness lift across the ladder

      Four models, four setups, three runs each. The results are on this page; rerun any time.

      npm run ex:6 -- --models llama3.2:3b,qwen3.5:9b --runs 3
    3. Add harder tasks

      Slugify is solved by anything from 9B up. Add five to ten harder tasks with hidden checks: fix a bug in existing code, change several files, follow a spec written in a file. Without them you can't measure harness changes on good models.

    4. Add loop detection and auto-verify

      The two harness upgrades most likely to move the numbers. Rerun the ladder after each one and keep the change only if scores go up.

    5. Add tree and edit_file tools

      Check that the explorer stops guessing paths in example 3, and that the builder breaks fewer files.

    6. Build the reviewer and the notes librarian

      Two read-only agents you can point at your own projects safely.
